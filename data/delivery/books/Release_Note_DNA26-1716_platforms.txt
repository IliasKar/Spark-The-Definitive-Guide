RELEASE NOTE - Platform Deliverables (DNA26-1716_platforms)
===========================================================

Scope: Cross-platform party-identity rule for the dtransfer deliverables,
portfolio_cdi_bal grain and settlement rework, and dtransfer_VatSettlement
corrections. 6 files changed.


WHAT CHANGED
------------

1) Party identity - PartyId / ParentPartyId (agreed cross-platform rule)
   Applied to dtransfer_customer, dtransfer_representatives, dtransfer_debtstatic,
   dtransfer_debtab:
   - PartyId = CDI (previously the source-system PartyKey/cust_id, which collided
     across source systems and silently mis-joined downstream). No DWH PartyId
     exists in the cloud; CDI is unique and non-colliding.
   - ParentPartyId = COALESCE(TaxRegistrationNumber, CDI) (previously NULL). The
     CDI fallback guarantees a non-null value.
   - Where a table has both a CDI and a PartyId column, both are populated with the
     same value.
   - No schema changes. IT confirmed the alphanumeric STRING domain for PartyId /
     ParentPartyId is accepted.
   - DebtStatic / DebtAB: the party match is now a LEFT SEMI gate on CDI (drops
     exposures with an unresolvable CDI, matching on-prem's INNER JOIN to Party);
     PartyId is taken from the exposure's own CDI.

2) portfolio_cdi_bal - grain and settlement fixes
   - uc_id and CDI are now two distinct columns with the on-prem fan-out grain.
     Balances are aggregated once per parent (uc_id = COALESCE(TaxRegistrationNumber,
     CDI)) and then fanned out to each individual CDI of the parent (one row per
     portfolio+CDI), matching on-prem (~385K rows vs on-prem 390,430).
   - Settlement participation fixed. Settlements now read from
     derivativeactive.dsettlementexposure (ParticipationPercentage fully populated)
     instead of primaryactive.settlementexposure (NULL for profits settlements). A
     fabricated default (COALESCE to 100) and a type-mismatch bug were removed;
     scaling is divide-by-100 on the unified 0-100 percent scale.
   - Settlement parent resolution now uses the party tax-number lookup directly
     (not the Primary-Owner-only dexposure), so guarantor/co-owner settlements are
     credited to their parent, matching on-prem.
   - Pre-write safety guards added: abort on an empty result; assert parent-grain
     vs fanned-out balance reconciliation; abort if the row count drops more than
     25% versus the currently delivered table.

3) dtransfer_VatSettlement
   - taxNumber NOT NULL contract enforced: party join is INNER on CDI, the dedup
     prefers a non-null tax number, plus an explicit non-null filter and assertion.
   - Loan-level only: AccountNumber = ExposureKey. Agreement-level settlements are
     excluded (their dash-composite AgreementKey is unmatchable against the on-prem
     account space). Agreements will follow later as a separate AgreementNumber
     column.

4) Robustness and documentation
   - Party-gate drop warning (prints when more than 1% of rows are dropped) in
     DebtStatic / DebtAB.
   - Invariant assertions: non-null PartyId; DebtStatic / DebtDetail / DebtFinancial
     share one LoanId set; portfolio+CDI uniqueness in portfolio_cdi_bal.
   - Migration checklist (steering) updated to the CDI identity rule.


IMPACT ON THE CONSUMING (PLATFORM) SIDE - ACTION REQUIRED
---------------------------------------------------------

1) PartyId / ParentPartyId are now STRING values (CDI / tax number), not integers.
   - On-prem Customer.PartyId, Representatives.PartyId, DebtStatic.PartyId and
     DebtAB.PartyId are int NOT NULL. The delivered values are now alphanumeric CDIs
     (e.g. GLC0004267942); roughly 89% are not integer-castable.
   - REQUIRED: widen these columns (and ParentPartyId) to a string type on the
     consuming side BEFORE loading. An int/positional load will fail or truncate.
     The 15+ modules that join Customer.PartyId = DebtStatic.PartyId continue to
     work, because both sides now carry CDI consistently.

2) portfolio_cdi_bal shape changed (breaking for naive readers).
   - A new uc_id column sits alongside CDI; the grain is now one row per
     portfolio+CDI, with the parent's balances repeated across its member CDIs.
   - REQUIRED: any row-level SUM over the table must GROUP BY uc_id first, otherwise
     totals are inflated (about 3% at row level - the same behaviour as on-prem).
     Column order aligns with on-prem (... off_balance_EUR, bal_over_settlement,
     initial_assign_bal_EUR).

3) dtransfer_VatSettlement is loan-level only (interim).
   - Agreement-level settlements are not delivered yet. If the consumer expects
     agreements, they will arrive in a later release as a separate AgreementNumber
     column (approximately 1-2 weeks).


DEPLOYMENT DEPENDENCY (BLOCKER)
-------------------------------
- The dsettlementexposure participation scaling must be unified to 0-100 for both
  qca and profits before portfolio_cdi_bal runs in production. Until then, profits
  rows are on a 0-1 scale and the divide-by-100 will under-scale them. Do not deploy
  portfolio_cdi_bal ahead of that change.


KNOWN / ACCEPTED DIFFERENCES
----------------------------
- portfolio_cdi_bal row count ~385K vs on-prem 390,430 (~1.3%, accepted
  party-coverage gap).
- Settlement total is below on-prem for parties whose settlement has no
  Primary-Owner output row - on-prem's MERGE also does not credit those.
- VatSettlement row coverage is lower than on-prem by design (on-prem agreement-level
  coverage is an on-prem-only implementation, not a cloud data gap).


VERIFICATION STATUS
-------------------
All changes were verified structurally and by SQL reconstruction against production
(p-cdh, business date 2026-10-30). They have NOT yet been executed end-to-end in
Databricks. A full run against an on-prem reference month is recommended before
release to confirm row counts, balance totals, and the new assertions/guards.
